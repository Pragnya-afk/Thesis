\chapter{Method}\label{sec:method}

This chapter describes the system we built and how we evaluate it. After an overview of the approach (Section~\ref{sec:overview}), we introduce what all variants share: the beat-based story representation and the shared story state (Sections~\ref{sec:beats} and~\ref{sec:state}). We then present the three variants in turn, the Baseline, the Director and the Time-Constrained Director (Sections~\ref{sec:baseline}--\ref{sec:tcdirector}), followed by two extensions, a beat generator and a lenient Director mode (Section~\ref{sec:extensions}), and a full-text variant of the Director that we use to test the beat representation (Section~\ref{sec:ablations}). The chapter closes with the characters and scenarios we use (Section~\ref{sec:characters}) and the design of our two evaluations, a user study and an LLM judge (Sections~\ref{sec:design-study} and~\ref{sec:design-judge}).

\section{Overview}\label{sec:overview}

The goal is a character that tells a coherent, in-character story, recovers when the user interrupts, and still finishes within a fixed time budget. Instead of one large architecture, we build three variants, each adding one component to the one before it: the Baseline, the Director, and the Time-Constrained Director. This way, the effect of each component can be measured on its own, and an improvement is not credited to several changes at once. All variants use the same language model (OpenAI's GPT-4o-mini), read the same character and scenario definitions, and go through the same evaluation pipeline, so any difference in the results comes from the architecture and not from the setup. We also built two extensions, a beat generator and a lenient Director mode. They are not part of the evaluation and are described in Section~\ref{sec:extensions}.

\section{Beat-Based Story Representation}\label{sec:beats}

We represent a story as an ordered list of beats. A beat is one narrative moment, written as a short name and a goal in plain language, for example \texttt{wolf\_appears}: ``Olaf introduces the wolf, setting the scene and the conversation.'' Because the goal is plain text, the language model can use it directly as context.

Beats are strictly linear. There is no branching and there are no parallel paths, which is enough for a single-character session of a few minutes. Each beat also carries an importance label (high, medium or low) and an optional list of expansions, which are small details the character may use to enrich the telling. The importance label matters only for the time-constrained variant (Section~\ref{sec:tcdirector}). The full beat schema is given in Appendix~\ref{app:beat-schema}.

All three variants use the same beats. The comparison therefore isolates the control mechanism and is independent of how the story is represented.

\section{Shared Story State}\label{sec:state}

The Director and Time-Constrained Director keep one story state object during a session. It records the index of the current beat, the beats completed so far, the number of turns spent in the current beat, and a running text of the story so far. For every turn, this text receives the user's input, the Director's decision and instruction, the character's reply, and a one-sentence summary of the story event. It serves as the character's memory of the story.

A beat ends when the Director marks it as complete, when the character reports that it has finished the beat, or when the character's reply already contains the next beat. The turn counter does not end a beat by itself. It is only passed to the Director as a pacing signal (Section~\ref{sec:director}).

\section{Baseline}\label{sec:baseline}

The Baseline is a single-agent design. On every turn, one model call receives the character profile, the full list of beats and the latest user input. It returns a JSON object with the character's reply, a one-sentence summary of the story event, an animation, and a flag saying whether the current beat is complete. The model alone decides when to move on to the next beat. In the user study, the Baseline additionally sees the current beat and the most recent part of the story.

The weakness of this design is that one call has to do everything at once. It must decide where the story goes, deal with the user's interruption, and perform the character. A language model has limited attention over its context, and it handles several tasks in one turn less reliably than a single one. Under repeated interruptions, the latest user message dominates the context, and the model tends to follow the user and lose track of the story.

\section{Director}\label{sec:director}

The Director variant separates deciding from performing. Each turn now consists of two model calls, made one after the other.

The first call is the \textbf{Director}, which decides what should happen next. It has no contact with the user and receives the following input:
\begin{itemize}
  \item the character profile,
  \item the entire beats list,
  \item the previous, current and next beat,
  \item the story so far,
  \item the user's input.
\end{itemize}
The Director is responsible for keeping track of the beats. It also keeps track of the beats.Its decision says whether the current beat should end, and the system then updates the current beat and the list of completed beats in the story state (Section~\ref{sec:state}). It returns a JSON object containing a decision type, whether the user interrupted, the user's detected intent, a short instruction for the character, whether the current beat should progress or end, and a brief reason for the decision. If this output cannot be parsed, the system falls back to a safe default: acknowledge the user briefly and add one new event to the current beat.

The second call is the \textbf{Character} (the actor), which carries out the Director's decision in its own voice, in two to four sentences. It sees the following:
\begin{itemize}
  \item the character profile,
  \item the current and next beat,
  \item the beats already completed,
  \item the story so far,
  \item the user's input,
  \item the Director's decision.
\end{itemize}
Unlike the Director, it does not see the entire beats list: it knows where the story is now and where it goes next, and its job is to perform the instruction rather than to decide what happens.

A single turn therefore runs as follows:
\begin{enumerate}
  \item The user sends a message.
  \item The Director is called with the user's message and the story state. The story so far contains all earlier user messages, Director instructions and character replies, but not yet the reply to the current message.
  \item The Director returns its decision, including the instruction for the character and whether the current beat should end.
  \item The Character is called with the user's message, the Director's decision and its part of the story state, and replies in character.
  \item The system appends the user's message, the Director's instruction and the character's reply to the story so far, and then checks whether the current beat has ended (Section~\ref{sec:state}). If so, it moves on to the next beat.
\end{enumerate}
The Director thus decides whether a beat should end before the character speaks, from the user's message and the story so far, while the beat itself only changes after the character has replied.

The Director chooses one of six decision types:

\begin{itemize}
  \item \textit{progress\_story}: work the user's input into the story and advance the current beat.
  \item \textit{answer\_and\_steer\_back}: answer a harmless side question in one short sentence and return to the story.
  \item \textit{elaborate\_in\_story}: give more detail about something that is already part of the story.
  \item \textit{gently\_redirect}: respond briefly to off-topic, repetitive or strongly derailing input, including attempts to stop the story, and then continue.
  \item \textit{advance\_beat}: move on to the next beat because the current one has been delivered.
  \item \textit{close\_story}: end the story, only once all beats are done.
\end{itemize}

Three rules keep the story moving. First, every turn must contain a new story development. When the character reacts to the user, it has to use a bridge sentence such as ``But back to what was happening\ldots'' to connect the reaction to the next event. Second, the Director is told how many turns have been spent in the current beat and is pushed harder to close it as that number grows. The turn count maps to one of four labels: on track (up to one turn), lingering (two turns), overdue (three to four turns) and stalled (five or more). Third, an opener guard stops the character from starting two turns in a row with the same word, or with a filler such as ``Oh'', ``Wow'' or ``Well'', which keeps the replies from becoming repetitive. The full prompt is in Appendix~\ref{app:director-prompt}.

\section{Time-Constrained Director}\label{sec:tcdirector}

The Time-Constrained Director adds a Temporal Monitor to the Director. The monitor is plain Python and makes no model calls. It compares the progress the story should have made, given by the fraction of the time budget that has elapsed, with the progress it has actually made, given by the fraction of beats completed. From the gap between the two it picks one of five pacing modes:

\begin{itemize}
  \item \textit{final}: less than a final buffer of time remains (30 seconds by default; in the user study, 20\% of the budget, kept between 30 and 60 seconds). The story is resolved in one closing message.
  \item \textit{too\_fast}: the story is ahead of schedule by at least 15 percentage points. The current beat stays open and is expanded with detail, emotion or character reactions, without adding new plot.
  \item \textit{critical}: the story is behind by at least 30 percentage points and at least one beat is done. The current beat ends now, and the next one or two beats are compressed into the same response.
  \item \textit{hurry}: the story is behind by at least 15 percentage points. The current beat should be finished.
  \item \textit{normal}: none of the above. The Director continues as usual.
\end{itemize}

The checks run in this order. The monitor passes the elapsed and remaining time, both progress values and the pacing mode to the Director as a temporal state, and the Director's prompt is extended with the rules for each mode. Under time pressure, the importance labels decide what is cut: high-importance beats are always narrated, medium ones can shrink to a sentence or two, and low ones can be merged into a neighbouring beat or dropped (Appendix~\ref{app:time-constrained-prompt}).

\section{Extensions}\label{sec:extensions}

Beyond the three variants, we built two extensions that remove two assumptions of the main system: that someone writes the beats by hand, and that the user may never stop the story. Both work with any of the three Director modes, but neither was part of the evaluation.

\subsection{Beat Generator}

Writing beats by hand takes time, so the beat generator creates them from a free-text story idea, for example ``Olaf tells the story of Cinderella''. A single call to GPT-4o receives the idea and the character profile and returns a story in the same format as our hand-written ones: a topic and a list of four to eight beats, aiming for about six. Every beat has a name, a goal, an importance label and three expansions. The prompt asks for a clear beginning, a rising development and a satisfying ending, and requires the first and last beat to be of high importance.

Language models do not always follow such a format, so a validation step repairs the output in code. It makes beat names unique, sets an invalid importance label to medium, fills in a placeholder for a missing goal or expansion, and trims stories with more than eight beats while keeping the most important middle beats. Every repair is logged as a warning, so a user can see what was changed. The result can be played directly by the Baseline, the Director or the Time-Constrained Director.

\subsection{Lenient Director}

The standard Director never lets the user stop or skip the story. It treats such requests as derailment and steers back. This is useful in an evaluation, but it is not how a real user wants to be treated, for example if someone already knows the story and asks to hear the ending. The lenient Director honours these requests, but only after confirmation, because stopping or skipping cannot be undone.

The lenient Director recognises three requests: to stop the story, to jump to the ending, and to hear a summary of the rest. It also has a fourth case, a nudge that asks ``would you like to keep going?'' when the user has drifted away from the story for a while. When a request is detected, the character asks the user to confirm. On the next turn, the model only classifies the user's reply as agreement, disagreement or an unrelated remark, judging by meaning and not by a fixed word list.

The decision itself is not left to the model. A small state machine written in code counts the confirmations and decides when to act, because the model proved unreliable at this in our tests. Stopping and jumping to the end need two confirmations, a summary and the continue nudge need one. A disagreement or an unrelated reply cancels the request and the story resumes. For a jump or a summary, the remaining beats are compressed into one closing response with the same rules as in the Time-Constrained Director: high-importance beats are narrated, medium ones get one sentence, and low ones are skipped. To make the model follow these rules, the section of the prompt that tells it to refuse stop requests is removed in code.

\subsection{Story Summary}

In long sessions, the story so far grows with every turn. To keep the Director's context short, the last six turns are passed on unchanged, and older turns are folded into a short summary of at most 200 words. The summary is updated every four turns by a separate model call. The character still receives the full text.

\section{Ablations}\label{sec:ablations}

Throughout this thesis, the target narrative is represented internally as a short ordered list of \emph{beats} : named units with a one-sentence goal each (e.g.\ \texttt{forest\_entry}: ``Red meets the wolf and reveals where she is going'')  rather than as a pre-written block of prose. The director tracks a \texttt{beat\_index} and a set of \texttt{completed\_beats}, and the director sees the list of beat names and goals together with the previous, current, and next beat, and the actor sees the current beat goal, the name of the next beat and the beats already completed, but neither is ever given the full text of what should eventually be said. We test this design choice directly, rather than asserting it.

We built a full-text variant of the director that is otherwise identical: the same decision-type taxonomy (\texttt{progress\_story}, \texttt{gently\_redirect}, \texttt{close\_story}, etc.), the same priority ordering, the same interruption-handling, anti-stall, and anti-repetition rules, the same actor style constraints. The only change is the representation of the story and how progress through it is tracked: the beat list and \texttt{beat\_index} are replaced with the complete prose text of the story and a self-reported ``turns since last advancement'' signal, and instead of the harness incrementing a counter when a beat is marked complete, the model must decide for itself, every turn, whether it has advanced through the text and when the story has genuinely ended.

\section{Characters and Scenarios}\label{sec:characters}

We use two characters. Olaf is warm, enthusiastic and playful, with a distinctive voice and a strong personality. Rocket Raccoon is sarcastic, brash and tech-savvy, which gives us a contrasting personality to test whether the results generalise. Both characters are well known, so any slip out of character is easy to notice, and both put the interruption handling under pressure in different ways.

For Olaf, we wrote a suite of 13 stories, each with its own beats (between 4 and 17), importance labels and a script of user inputs (between 4 and 30). Every story exists in three versions that differ in how much the user derails:

\begin{itemize}
  \item \textit{No derailment}: all inputs are on topic and move the story forward.
  \item \textit{Medium derailment}: half of the inputs are completely off topic, for example ``What is your favorite color?''.
  \item \textit{Complete derailment}: all inputs are off topic, which is the maximum stress test.
\end{itemize}

Because the inputs are scripted, every system sees exactly the same user and the runs can be repeated.

\section{User Study Design}\label{sec:design-study}

28 people took part in the study. Each participant played through two short interactive stories narrated by an LLM-driven Olaf, each story twice, under a different narrative-control condition each time (there was only text output and no audio output). Participants were members of Disney Research Studios and the Game Technology Center (GTC) at ETH Zurich. A full session took about 25 to 30 minutes, and responses were saved anonymously.

\begin{itemize}
\item \textbf{Story 1 -- Frozen} (5 narrative beats): once under \textbf{Baseline} (Olaf responds directly to the user, with no structural guardrails), once under \textbf{Director} (a beat-based director agent steers every turn toward the next story beat while trying to accommodate the user).
\item \textbf{Story 2 -- Cinderella} (9 narrative beats): once under the same \textbf{Director} condition, once under \textbf{Time-Constrained Director} -- identical director logic, but additionally paced against a fixed 3-minute target, instructed to compress or fold together lower-importance beats as time runs out.
\end{itemize}

Condition order was randomized independently per participant and per story, so order is not confounded with condition. Of the 28 participants, 14 completed all four rounds and the closing questionnaire; all analyses in Chapter~\ref{sec:results} that require a within-subject pairing use these 14 completers, since they are the only participants who rated every condition.

The welcome screen (Figure~\ref{fig:study-welcome}) was the only instruction participants received. It explained the two stories and the questionnaire after every round, and explicitly asked participants to try to derail the conversation (``go off-topic, ask him something random, bring up a different subject''). Participants were encouraged, but not forced, to do so, so every measure of derailment resistance in Chapter~\ref{sec:results} reflects deliberately provoked interruption, not incidental drift.

\section{LLM-as-Judge Evaluation Design}\label{sec:design-judge}

The second assessment is an automated one. It lets us test many more stories, and with controlled derailment, than a live study can cover. An LLM judge reads transcripts and scores them, in two modes.

\subsection{Judge and Rubric}

We use OpenAI's GPT-4o as the judge, with the sampling temperature set to zero. It is the most recent model that still lets us set the temperature, and it is the judge used in the CoDi paper, on which our procedure is based. As a robustness check, we also repeat one comparison with GPT-5.6-sol (Section~\ref{sec:judge-model-comparison}). This model was released after this thesis began, so we use it only for this check and leave a more thorough investigation to future work. The judge scores eight core dimensions: plot, development, language use, interruption handling, character fidelity, narrative control, anthropomorphism and a holistic overall score. Plot asks for a clear beginning, middle and end. Development asks whether characters and setting are introduced in enough detail. Language use looks for varied, in-character wording. Interruption handling checks that off-topic input is acknowledged briefly and the thread is resumed without breaking character. Character fidelity checks for a consistent personality, and narrative control asks for steady progress through the beats and a satisfying ending. Anthropomorphism asks whether the character feels like an autonomous agent and not a tool serving the user. Three further dimensions were added for the comparison with CoDi and six for the time-budget experiments. All of them are listed in Table~\ref{tab:rubric}.

Most of these dimensions are not new. We take them from the evaluation protocol of CoDi \cite{kim2025codi}, which in turn uses plot, development, language use and overall quality from Agents' Room \cite{huot2025agents}, and anthropomorphism and character fidelity from CoSER \cite{wang2025coser}. Interruption handling and narrative control are our own additions. They measure what this thesis is about, namely how a character reacts to derailment and whether the story keeps moving.

For the comparison with CoDi, we added three dimensions. CoDi and our system produce different kinds of text. CoDi writes a complete story and passes it through an editor agent that formats it as a screenplay or novel, while our system produces short turns in reaction to a user. A rubric that only judges plot and character would miss this difference. Detail and thoroughness and narrative polish capture how rich and finished the prose is, and director decision-making compares how clearly the two Directors guided their stories.

For the time-budget experiments, we added six more dimensions. With a short budget, the Time-Constrained Director has to compress the story, and the core rubric cannot tell whether the compression kept the story intact. The added dimensions check exactly that: whether the amount of detail suits the budget (descriptiveness), whether each beat is still honoured in substance (beat fidelity), whether the cuts between scenes feel natural (transition quality), whether a beginning, middle and end survive (three-act balance), whether what the story sets up is still paid off (setup and payoff preservation), and whether the emotional tone changes over the story (emotional arc). These dimensions are used in addition to the core ones.

\subsection{Single-Story and Pairwise Scoring}

In single-story mode, the judge gives each dimension a score out of ten together with a written justification. Each condition is run five times and the scores are averaged, which reduces the variance caused by sampling in the generation.

In pairwise mode, the judge sees two transcripts, Story A and Story B, and picks A, B or Same for each dimension. LLM judges tend to prefer whichever story comes first \cite{zheng2023judging}, so every pair is judged twice, once as (A, B) and once as (B, A). A dimension only gets a winner if both verdicts agree after the labels are translated back. Otherwise, it counts as Same. Win rates are then aggregated over the five run pairs of a condition.

\subsection{Experimental Conditions}

We evaluate three systems (Baseline, Director and Time-Constrained Director) at the three derailment levels. The Time-Constrained Director runs with time budgets of 0.5, 2, 5 and 10 minutes, while the other two have no time limit. Each condition is run five times with the scripted user inputs. We run seven comparisons, all with the same rubric and the same order-bias-controlled protocol. The results are in Section~\ref{sec:llm-judge}.

\begin{itemize}
\item \textbf{Baseline vs.\ director} (Section~\ref{sec:llm-baseline}) — 30 transcript pairs: 10 Olaf story scenarios, each played at three derailment levels (none, medium, complete).
\item \textbf{Director vs.\ CoDi} (Section~\ref{sec:llm-codi}) — the same 30 Olaf transcript pairs, comparing our Director with CoDi \cite{kim2025codi}, judged with the core rubric and the three dimensions added for this comparison.
\item \textbf{Time-budget ablation} (Section~\ref{sec:llm-timebudget}) — the Time-Constrained Director at budgets of 0.5, 2, 5 and 10 minutes against the unconstrained Director, 30 scenarios per budget, judged with the time-budget dimensions.
\item \textbf{Second character: Rocket Raccoon} (Section~\ref{sec:llm-rocket}) — the baseline-vs-director comparison repeated for a different character on 7 scenarios. A scenario here is one story, Red Riding Hood, played with a different scripted set of derailment inputs, so the 7 scenarios share the story and differ only in how the user derails it.
\item \textbf{Beats vs.\ full-text director} (Section~\ref{sec:llm-beats-ablation}) — 7 transcript pairs on the same 7 Red Riding Hood scenarios (one story, 7 different derailment inputs), with Olaf, isolating the choice of story representation.
\item \textbf{Judge model robustness} (Section~\ref{sec:judge-model-comparison}) — baseline vs.\ director at each derailment level, judged by both GPT-4o and GPT-5.6-sol.
\item \textbf{Cross-check against the live study} (Section~\ref{sec:llm-vs-study}) — the exact Frozen and Cinderella stories from the user study under complete derailment, 5 runs per condition.
\end{itemize}

\subsection{Cross-Check Against the User Study}\label{sec:design-crosscheck}

For this cross-check, the automated side uses each story's \emph{complete-derailment} scenario variant, since the user study's welcome screen explicitly encouraged participants to ``go off-topic, ask him something random, bring up a different subject'' in every round (Section~\ref{sec:design-study}), so every live rating already reflects a story under sustained, deliberate derailment pressure. The complete-derailment automated variant is the one built to match that: it scripts the heaviest, most persistent stream of off-topic user turns in the suite.

Story 1 (Section~\ref{sec:story1}), called Frozen in the user study, is \texttt{olaf\_retells\_frozen\_1\_complete\_derailment}, director vs.\ baseline. Story 2 (Section~\ref{sec:story2}), called Cinderella in the user study, is \texttt{olaf\_retells\_cinderella\_complete\_derailment}, director vs.\ a time-constrained director. Each condition is generated and judged five separate times, and the numbers reported are the mean of those five runs. This is to smooth out the noise and give a stable estimate of how the LLM judges each condition.

The five core measures used in the comparisons in Section~\ref{sec:llm-vs-study} (Q1, Q2, Q3, Q4, Q6) fall into three groups. Q1, Q2, and Q4 have a clean one-to-one judge dimension (Plot, Character Fidelity, Overall respectively). Q6 has no single equivalent -- it spans both Interruption Handling (does the character acknowledge and recover from the interruption) and Narrative Control (does the story keep moving toward its beats regardless) -- so the discussion there reads it against both rather than picking one. Q3 has no direct equivalent and is only loosely approximated by Language Use and Anthropomorphism, so it is not compared directly.
